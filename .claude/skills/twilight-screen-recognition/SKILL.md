# 화면 인식·게임 감지 (로드맵 M3~M5)

설계의 원본은 `DESIGN.md` §4(파이프라인), §4.7(빠른 스킵 대응), §5(게임별 화면 정의)다. 구현 전에 해당 절을 읽는다. 이 스킬은 구현할 때 지킬 원칙과 순서를 정리한다.

## 원칙 (사용자와 합의됨)

- **트래커가 화면을 읽고 스스로 판단**하고, 수동 입력은 수정용이다.
- 게임 메모리·통신·계정 로그인은 쓰지 않는다. 화면 캡처만 쓴다.
- 순간적으로 지나가는 화면(연출, 교환 확인창)은 보조 정보다. **결과 요약 화면과 재화 잔액**처럼 사라지지 않는 상태를 기준으로 하고, 잔액으로 다시 계산해 맞춘다.
  - 뽑은 횟수 = 줄어든 티켓 + 줄어든 유료 재화 ÷ 1회 비용
  - 창세의 결정 사용량 = 뽑기 후 원석 − 뽑기 전 원석 + 160 × 원석으로 뽑은 횟수
- 확신이 낮으면 멈추지 않고 **확인 대기**(`Pull.status = "pending"`)로 보낸다. 결과를 놓친 구간은 "빈 구간"으로 둔다.
- 화면 영역은 **창 크기 대비 비율**(0~1)로 정의한다. 기기마다 해상도가 다르다.
- 화면 이미지는 기기 밖으로 보내지 않는다. 확인 대기 항목의 작은 크롭만 저장하고, 확정되면 지운다.

## 안드로이드 구현 순서

1. **M3 게임 감지: 취소됨(2026-11-25).** 안드로이드에서 `UsageStatsManager`(사용 기록 권한)는 쓰지 않는다. 게임은 사용자가 고르고, 화면 인식이 들어오면 화면 내용(배너·재화 영역)으로 어떤 게임인지 판단해 전환한다. PC의 프로세스 감지는 유지.
2. **M4 캡처 + 재화 OCR — 뼈대 완료(0.4.0, 실기 미확인)**
   - `ScreenReadService.kt`: `CaptureConsentActivity`(투명)로 동의 창 → `MediaProjection` + `ImageReader`(긴 쪽 1280px) → 2.5초마다 ML Kit 한국어 인식(`play-services-mlkit-text-recognition-korean`, 모델은 플레이 서비스가 내려받음. 앱에 넣는 방식은 APK 47MB라 쓰지 않음) → 줄 단위 `{t, x, y, w, h}`(비율) JSON → `OverlayService.screenText` → 웹의 `window.__twilightScreen`.
   - `src/lib/recognize.ts`(순수 함수, 테스트 있음): 버튼 글자("10회 헤드헌팅", "10회 추출", "기원 10회", "10회 진행")로 게임과 가챠 메인 화면을 판단하고 재화·배너·남은 횟수를 뽑는다.
   - `ScreenPanel.svelte`("확인" 화면 안): 켜기/끄기, 읽은 내용, "읽은 재화로 맞추기"(사용자가 눌러야 적용), "읽은 글자 복사"(사용자가 실제 인식 결과를 보내 줄 수 있게).
   - 0.4.1: "띄우기"를 누를 때 `MainActivity`가 동의 창을 바로 띄워 함께 시작한다(설정 `autoScreenRead`, 기본 켜짐. 동의는 안드로이드 규칙상 매번 필요). 결과 수신은 `App.svelte`가 맡아 창이 접혀 있어도 받는다.
   - **실기 결과(사용자, 2026-11-25)**: 읽기 자체는 동작. 원신은 원석 대신 스타라이트·스타더스트를 집음(규칙 오류, 실제 "읽은 글자" 필요). 명일방주 창고는 아이템 이름 글자가 없어 못 읽음 → 사용자 결정으로 허가증은 직접 입력 전용으로 정리(창고 읽기 안 함).
   - 0.4.3(실기 결과 반영): **펼친 창이 떠 있으면 읽지 않고**(게임을 가리고, 창 글자를 게임 글자로 읽었음), 접힌 막대 자리는 검게 지운 뒤 읽는다(`OverlayService.overlayRect`). 게임이 가로로 돌면 찍는 화면도 돌린다. 원신 오른쪽 위는 숫자가 4개(스타라이트·스타더스트·원석+·인연 순서, **사용자 확인**)라 **"+"가 붙은 숫자 = 원석**, 그 오른쪽 마지막 = 인연. 림버스 발푸르기스는 "WALPURGISNACHT - X"의 로마 숫자로 회차를 읽는다. 사용자가 보낸 실제 인식 결과는 `src/lib/fixtures/*.txt`에 두고 테스트한다(글자뿐이라 저장소에 넣어도 됨).
   - 0.4.4(실기): 명일방주 위쪽 오른편 = 용문폐, 공개모집 허가증(?), **오리지늄 교환 칸(보유 오리지늄 × 180이 적힘)**, 합성옥. 배너는 "…에 종료합니다" 위 줄. 엔드필드 파생 오리지늄 뒤 "+" 때문에 숫자 줄로 안 읽히던 문제 → 숫자 조각으로 읽음. 엔드필드 허가증 2칸일 때 앞=한정 헤드헌팅 허가증, 뒤=기간 한정 허가증(**사용자 확인**). 명일방주 2번째 칸 = 공개모집 허가증(사용자 확인, 읽지 않음). **엔드필드도 교환 칸 = 파생 오리지늄 × 75(오로베릴 환산), 맨 오른쪽[+] = 오로베릴**(사용자 확인 2026-11-25). "읽은 글자 복사"는 가챠 화면으로 보이는 프레임만 남긴다(사용자가 다른 앱 화면을 복사한 일이 있었음).
   - **실기 동작 확인(사용자, 2026-11-25)**: 원신(원석·인연), 림버스(광기·발푸르기스 배너)는 0.4.3에서 정상. 명일방주·엔드필드는 0.4.5 확인 대기.
   - **0.5.0 뽑기 감지** (`src/lib/detect.ts`, 테스트 있음): 메인 화면 재화가 **두 번 연속 같게** 읽혀야 믿고(한 번 잘못 읽힌 숫자 무시), 직전 값보다 줄면 차감 순서(`spend`)로 횟수를 센다. 화면에 안 나오는 재화(티켓 등)나 나눠떨어지지 않는 감소는 `uncertain`. 결과는 기록이 아니라 "확인" 화면의 감지 카드(`DetectionCard.svelte`, 종류·횟수 수정 가능)로 가고, 사용자가 "기록"을 눌러야 `recordDetected`로 들어간다. 감지 목록은 기기 안 `localStorage["tg-detections"]`.
   - **원신 공개 화면 이름**: 왼쪽 가운데(x<0.45, 0.25<y<0.8) 줄이 `data/genshin-items.json`(paimon.moe에서 생성, 이름→등급·종류, 369개)의 이름을 포함하면 그 아이템. 같은 화면이 여러 번 읽혀도 한 번만 센다(그래서 같은 3성 무기가 연달아 나오면 하나로 합쳐질 수 있음). 최고 등급은 묶음 안 맨 뒤 자리에 둔다(실제 위치 모름 → 천장이 최대 9 적게 계산될 수 있음).
   - **3성은 기록·표시하지 않는다(사용자 요청 2026-11-25).** 표에는 남겨 두고 공개 화면 수 ↔ 횟수 확인용으로만 쓴다.
   - 4성은 `Pull.rarity = 4` + 이름으로 남고, 최근 뽑기 줄에 보라색, 통계에 "4성 기록"으로 보인다.
   - 0.5.3: **읽는 간격 자동 조절**(사용자 선택): 인식 글자에 가챠 관련 단어(헤드헌팅|기원|추출|회 진행|LUNACY|UID)가 보이면 그 뒤 20초 동안 1초 간격, 아니면 2.5초. 뽑기 감지는 같은 값 2번 연속이 필요하므로 가챠 화면에서 약 2초면 충분.
   - 0.5.4: 믿을 수 있는 마지막 재화(`stable`, `stableAt`)를 `localStorage["tg-detect-state"]`에 저장해 앱을 다시 켜거나 가챠 화면을 열자마자 뽑아도 비교할 기준이 있다. 기준이 10분보다 오래됐으면 `uncertain`.
   - **0.6.0 재화 자동 반영**: 두 번 연속 같게 읽힌 재화(`stable`)는 바로 `setCurrency`로 앱에 반영(사용자 요청). "읽은 재화로 맞추기" 버튼은 남겨 둠.
   - **0.6.0 엔드필드 공식 기록 읽기** (`src/lib/history.ts`, 실기 자료 `fixtures/endfield-history-phone.txt`): "헤드헌팅 기록" 화면은 한 쪽에 5줄, 열은 배너(x≈0.3) / 이름(x≈0.55) / 시간(x≈0.71, "시간 (UTC+8)" 머리글). "긴급 모집-<배너>"는 무료 10회라 천장에 안 넣음. 등급은 글자로 안 나와 **6성 이름 목록**(`data/names/endfield-6star.json`, 공지에서 자동 수집)으로 판별. 쪽 번호로 같은 쪽 중복 제거, "확인" 화면의 기록 카드 → "기록에 반영"(`importHistory`: 덮는 시간대의 기존 뽑기를 공식 기록으로 교체, 되돌리기 가능). 배너는 배너 자료의 「이름」으로 종류를 찾고, 못 찾으면(기초 헤드헌팅) 제외.
   - 아직 없음: 자동 기록, 뽑기 전후 재화 비교, 결과 화면 인식. 실기에서 받은 "읽은 글자"로 규칙을 맞춘 뒤 진행한다.
3. **M5 결과 인식**: 등급은 색(엔드필드 레버: 보라=4성, 노랑=5성, 빨강=6성 / 원신 유성: 파랑·보라·금색), 개수는 요약 화면 카드 수, 이름은 일러스트 특징값 비교(처음 보는 것은 확인 대기 → 사용자가 고치면 학습). 결과는 웹 쪽 장부(`ledger.ts`)에 `source: "screen"`, `confidence`와 함께 넣는다.

- 다른 트래커(goyfield, aktracker)는 로그인 토큰을 꺼내 서버에 넘기거나 브라우저 확장으로 페이지를 읽는다. **우리는 토큰·로그인 정보를 다루지 않는다**(원칙, 같은 방식의 다른 사이트가 악성 코드로 문제된 사례도 글에 있음). 대신 사용자가 그 페이지를 휴대폰 브라우저로 직접 열면 **화면 읽기로 글자를 읽는다** — 게임 안 기록 화면 읽기와 같은 방식.
- 운 비교는 "사이트 전체 이용자 대비 %"가 인기 기능이다. 우리는 원격 수집을 하지 않으므로 친구 공유(M9)에서 친구끼리만 비교한다. 픽업 배너는 운 측정이 왜곡되기 쉽다는 의견도 참고.

## 레퍼런스와 테스트

- 좌표·색 기준은 반드시 **사용자 기기의 실제 스크린샷**으로 정한다. 받으면 `references/`가 아니라 테스트 고정 데이터(fixtures)로 저장하되, 공개 저장소에 올려도 되는지 사용자에게 먼저 묻는다(게임 화면 이미지).
- 판별 로직은 스크린샷을 입력으로 받는 순수 함수로 만들어 단위 테스트한다(캡처·OCR과 분리).
- 디자인 참고용 화면은 `twilight-game-reference`의 YouTube 프레임으로 구할 수 있지만 좌표 기준으로는 쓰지 않는다.
